# Release evidence chain

Three files, generated in this order, none of them hand-typed:

```text
restore-proof.json
    -> generated by ops/generate-restore-proof.ps1
    -> only after a real, successful restore onto a local PostgreSQL 17
       rehearsal clone, reviewed by the operator (-Confirmed)

staging-rehearsal-proof.json
    -> generated by ops/generate-staging-rehearsal-proof.ps1
    -> only after a real, successful run of
       ops/run-prelaunch-release-core.ps1 against the staging target
    -> chained to restore-proof.json via restore_proof_sha256

owner-go.json
    -> generated by ops/record-owner-go.ps1
    -> only after the owner reviews the staging proof summary and types
       the exact confirmation phrase
    -> chained to staging-rehearsal-proof.json via staging_proof_sha256
```

None of these files exist in this repository yet -- R0 is not closed and no
rehearsal has run. This directory holds only this README until a real
rehearsal produces real evidence.

## Why generation, not templates

Every field in every file above is either copied verbatim from a manifest
already committed to the repository, or computed with `Get-FileHash` against
a file on disk at generation time. Nothing is typed in as a hash by a human.
`ops/run-prelaunch-release-core.ps1` re-derives every one of these values
independently at production-run time and refuses to proceed
(`STOP_PRODUCTION_RELEASE_NOT_AUTHORIZED`) on any mismatch, missing field, or
placeholder-looking value -- before any credential is requested.

## Why these files are not committed ahead of time

A committed "example" with plausible-looking hashes would be indistinguishable
from real evidence to a careless reviewer. The generator scripts are the only
supported way to produce these files, and they refuse to run against anything
but real, already-completed rehearsal artifacts on disk.
